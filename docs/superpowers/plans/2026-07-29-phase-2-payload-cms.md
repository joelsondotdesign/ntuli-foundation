# Phase 2 — Payload CMS Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the Foundation a working `/admin` on their own domain — email/password login, user management with roles, a media library, and the four content types — without touching the public site.

**Architecture:** Payload 3.86 runs inside the existing Next.js 16 app. Payload's files live in a `(payload)` route group; the six public pages move into a `(site)` route group so each has its own root layout. Content is stored in Neon Postgres (Frankfurt), media in Vercel Blob. Nothing on the public site reads from the CMS yet — that is Phase 3.

**Tech Stack:** Payload 3.86 · `@payloadcms/db-postgres` · `@payloadcms/richtext-lexical` · `@payloadcms/storage-vercel-blob` · Neon Postgres · Nodemailer over the Foundation's existing SMTP

## Global Constraints

- **Next stays `>=16.2.6 <17.0.0`.** `@payloadcms/next@3.86.0` requires exactly that range. All `@payloadcms/*` packages must be pinned to the same version, `3.86.0`.
- **All six public routes keep their existing URLs and stay statically generated.** Route groups do not affect URLs: `src/app/(site)/what-we-do/page.tsx` still serves `/what-we-do`. Any route that goes dynamic is a defect.
- **`public/assets/css/main.css` must not change.** It differs from the pre-port original by exactly 8 bytes and stays that way. Payload's admin styling is entirely separate and must not leak into the site, or the site's into it.
- **No public page may import from `payload` or query the database in this phase.** Phase 3 does that. If a page file changes at all in Tasks 3–11, something has gone wrong.
- **Secrets never enter the repo.** `DATABASE_URL`, `PAYLOAD_SECRET` and the SMTP credentials live in `.env.local` (git-ignored) and, later, Vercel environment variables. Never commit a value, never paste one into a report.
- Site origin `https://www.ntulifoundation.org`; language `en-ZA`; British/South African spelling in all admin-facing labels and help text.
- The client is non-technical. Every field label and description in the admin is written for them, not for a developer.

### Task 1: Move the public site into a `(site)` route group

**Files:**

**Interfaces:**
- Consumes: nothing
- Produces: `src/app/(site)/layout.tsx` as the site's root layout; `src/app/` free for Payload's `(payload)` group

**Route groups do not change URLs.** `(site)` is parenthesised, so it is invisible to routing. Every URL must be byte-identical afterwards — that is this task's whole test.

### Task 2: Extract the cookie notice and theme toggle from SiteScripts

**Files:**
- Create: `src/components/CookieNotice.tsx`, `src/components/ThemeToggle.tsx`
- Modify: `src/components/SiteScripts.tsx` (remove both blocks), `src/components/SiteChrome.tsx` (render `<CookieNotice />`), `src/components/Footer.tsx` (render `<ThemeToggle />`)

**Interfaces:**
- Consumes: nothing
- Produces: `<CookieNotice />` and `<ThemeToggle />`, both client components taking no props

**Why now, before any CMS work.** `SiteScripts` reaches out of the React tree with `document.querySelector` for nine selectors and toggles classes imperatively. That is safe today because every page's DOM is static after mount. From Phase 3 it will not be: a revalidation can replace a node underneath `is-in`/`is-stuck`/`is-open` and the imperative state is silently lost. The final Phase 1 review recommended doing this **before** content becomes dynamic. The cookie notice and theme toggle are the two pieces that own discrete, self-contained state, so they extract cleanly; the sticky nav, reveals and GSAP timelines are genuinely global and stay put.

The cookie notice is also about to become CMS-controlled — Site Settings has a visibility toggle for it in Task 9 — so it needs to be a component that can take a prop.

**Behaviour that must not change.** From `public/assets/js/main.js` as ported:
- Cookie notice: if `localStorage["ntuli-cookie-choice"]` is set, it is removed immediately; otherwise `is-in` is added after **1600ms**, and on choosing, the choice is stored, `is-in` removed, and the element removed after **700ms**.
- Theme toggle: flips `data-theme="dark"` on `<html>` and writes `localStorage["ntuli-theme"]`, wrapped in `try/catch`. The pre-paint script in the layout reads the same key.

- [ ] **Step 1: Write `CookieNotice.tsx`**

Markup transcribed from the current `SiteChrome.tsx`.

```tsx
"use client";

import { useEffect, useState } from "react";

export default function CookieNotice() {
  const [decided, setDecided] = useState(true);
  const [shown, setShown] = useState(false);

  useEffect(() => {
    let stored: string | null = null;
    try {
      stored = localStorage.getItem("ntuli-cookie-choice");
    } catch {}
    if (stored) return;
    setDecided(false);
    const t = window.setTimeout(() => setShown(true), 1600);
    return () => window.clearTimeout(t);
  }, []);

  useEffect(() => {
    if (!decided || shown) return;
    const t = window.setTimeout(() => setShown(false), 700);
    return () => window.clearTimeout(t);
  }, [decided, shown]);

  const choose = (choice: string) => {
    try {
      localStorage.setItem("ntuli-cookie-choice", choice);
    } catch {}
    setShown(false);
    window.setTimeout(() => setDecided(true), 700);
  };

  if (decided && !shown) return null;

  return (
    <aside className={`cookie${shown ? " is-in" : ""}`} role="region" aria-label="Cookie notice">
      <p>We use a small number of cookies to understand how the site is used. Nothing is sold, and nothing is shared with advertisers.</p>
      <div className="cookie-actions">
        <button className="decline" data-choice="declined" type="button" onClick={() => choose("declined")}>Decline</button>
        <button className="accept" data-choice="accepted" type="button" onClick={() => choose("accepted")}>Accept</button>
      </div>
    </aside>
  );
}
```

- [ ] **Step 2: Write `ThemeToggle.tsx`**

```tsx
"use client";

export default function ThemeToggle() {
  const toggle = () => {
    const wasDark = document.documentElement.getAttribute("data-theme") === "dark";
    if (wasDark) document.documentElement.removeAttribute("data-theme");
    else document.documentElement.setAttribute("data-theme", "dark");
    try {
      localStorage.setItem("ntuli-theme", wasDark ? "light" : "dark");
    } catch {}
  };

  return (
    <button className="theme-toggle" data-theme-toggle type="button" aria-label="Switch between light and dark mode" onClick={toggle}>
      <svg className="moon" viewBox="0 0 24 24" fill="none" aria-hidden="true">
        <path d="M21 12.8A9 9 0 1 1 11.2 3a7 7 0 0 0 9.8 9.8Z" stroke="currentColor" strokeWidth="1.8" strokeLinecap="round" strokeLinejoin="round" />
      </svg>
      <svg className="sun" viewBox="0 0 24 24" fill="none" aria-hidden="true">
        <circle cx="12" cy="12" r="4" stroke="currentColor" strokeWidth="1.8" />
        <path d="M12 2v2M12 20v2M4.9 4.9l1.4 1.4M17.7 17.7l1.4 1.4M2 12h2M20 12h2M4.9 19.1l1.4-1.4M17.7 6.3l1.4-1.4" stroke="currentColor" strokeWidth="1.8" strokeLinecap="round" />
```

### Task 4: Users — auth, roles, and access control

**Files:**
- Create: `src/collections/Users.ts`
- Modify: `payload.config.ts` (register the collection)

**Interfaces:**
- Consumes: `payload.config.ts` from Task 3
- Produces: collection slug `users`, with fields `name` (text), `role` (select: `admin` | `editor`), plus Payload's built-in `email` and password. Later tasks import `isAdmin` and `isAdminOrSelf` from this file.

**The requirement, from the spec:** *"Editor: manages content. Admin: manages content **and** users. Only Admins see the Users section, so an Editor cannot lock anyone out."*

- [ ] **Step 1: Write the collection**

```ts
import type { Access, CollectionConfig } from "payload";

export const isAdmin: Access = ({ req: { user } }) => user?.role === "admin";

export const isAdminOrSelf: Access = ({ req: { user }, id }) => {
  if (!user) return false;
  if (user.role === "admin") return true;
  return user.id === id;
};

export const Users: CollectionConfig = {
  slug: "users",
  auth: {
    tokenExpiration: 60 * 60 * 8,
    maxLoginAttempts: 5,
    lockTime: 10 * 60 * 1000,
  },
  admin: {
    useAsTitle: "name",
    defaultColumns: ["name", "email", "role"],
    group: "Settings",
    hidden: ({ user }) => user?.role !== "admin",
  },
  access: {
    read: ({ req: { user } }) => Boolean(user),
    create: isAdmin,
    update: isAdminOrSelf,
    delete: isAdmin,
    admin: ({ req: { user } }) => Boolean(user),
  },
  fields: [
    {
      name: "name",
      type: "text",
      required: true,
      admin: { description: "The name shown next to anything this person publishes." },
    },
    {
      name: "role",
      type: "select",
      required: true,
      defaultValue: "editor",
      options: [
        { label: "Editor — can add and edit content", value: "editor" },
        { label: "Admin — can also manage who has access", value: "admin" },
      ],
      access: { update: isAdmin },
      admin: { description: "Only an Admin can change this." },
    },
  ],
};
```

`access.update: isAdminOrSelf` lets an editor change their own name and password but nobody else's. `role` carries its own `access.update: isAdmin`, so an editor cannot promote themselves even on their own record — that combination is the point, and it is what Step 4 tests.

- [ ] **Step 2: Register it**

In `payload.config.ts`, import `{ Users }` and set `collections: [Users]`.

- [ ] **Step 4: Test the access rules for real**

- [ ] **Step 1: Write the parser**

```ts
export type YouTubeRef = { id: string; start?: number };

const ID = /^[A-Za-z0-9_-]{11}$/;

/** Seconds from a YouTube time param: "44", "44s", "1m30s", "1h2m3s". */
function parseStart(raw: string | null): number | undefined {
  if (!raw) return undefined;
  if (/^\d+$/.test(raw)) return Number(raw);
  const m = raw.match(/^(?:(\d+)h)?(?:(\d+)m)?(?:(\d+)s)?$/);
  if (!m || (!m[1] && !m[2] && !m[3])) return undefined;
  const secs = Number(m[1] || 0) * 3600 + Number(m[2] || 0) * 60 + Number(m[3] || 0);
  return secs || undefined;
}

/** Accepts any ordinary YouTube URL, or a bare 11-character video id. */
export function parseYouTube(input: string): YouTubeRef | null {
  const raw = input.trim();
  if (!raw) return null;
  if (ID.test(raw)) return { id: raw };

  let url: URL;
  try {
    url = new URL(raw.startsWith("http") ? raw : `https://${raw}`);
  } catch {
    return null;
  }

  const host = url.hostname.replace(/^www\./, "");
  let id: string | null = null;

  if (host === "youtu.be") id = url.pathname.slice(1);
  else if (host.endsWith("youtube.com")) {
    if (url.pathname === "/watch") id = url.searchParams.get("v");
    else {
      const m = url.pathname.match(/^\/(?:embed|shorts|live|v)\/([^/?#]+)/);
      if (m) id = m[1];
    }
  }

  if (!id || !ID.test(id)) return null;
  const start = parseStart(url.searchParams.get("t") || url.searchParams.get("start"));
  return start ? { id, start } : { id };
}
```

## What Phase 2 deliberately does not do

No public page reads from the CMS. No content is migrated. No article pages, no section toggles taking effect, no `sitemap.xml`, no populated `sameAs`, no preview. The public site at the end of Phase 2 is byte-identical to the end of Phase 1 — the CMS simply exists alongside it, with the client able to log in and enter content that nothing yet displays.

That is deliberate. It means if the site breaks in Phase 3, the cause is the wiring, not the CMS.
